# Gaia Project RL 에이전트 — 설계 명세

이 문서는 여러 세션에 걸친 대화에서 결정된 것들을 한 곳에 모아둔 것이다. 코드가 아니라
"왜 이렇게 하기로 했는지"를 남기는 목적이 크다 — 특히 트레이드오프 판단은 대화 없이
코드만 봐서는 복원이 안 되기 때문.

## 목표

4인 고정 + Lost Fleet 확장 고정 Gaia Project를, 게임이 진행될수록 강해지는 셀프플레이
강화학습 에이전트로 플레이하게 만든다. 네트워크/서버 경유 없이 `gaia-engine`을
라이브러리로 직접 호출하는 자체 시뮬레이션으로 훈련한다.

## 게임 업데이트와 시뮬레이터 버전

초기에는 게임 엔진 변경이 많아 어댑터 착수를 미뤘지만, 현재는 승인된 계획에 따라
구현 중이다. 실행 중인 Rust 시뮬레이터는 빌드된 규칙을 사용하며, 편집 중인 게임 소스를
실시간으로 불러오지 않는다.

- 엔진·어댑터 소스 및 Cargo 설정의 SHA-256을 `ENGINE_BUILD_ID`와 소스 manifest로 기록.
- `gaia_rl.versions.require_current_sources(root)`로 새 실행 전 소스/빌드 차이를 검사.
- Python 코드도 별도 fingerprint를 만들고, 저장된 버전과 다르면 재개를 거부하는
  `require_compatible_versions`를 학습 실행기/체크포인트 재개/추론에 연결했다.
- 이미 실행 중인 시뮬레이션을 소스 편집 때문에 중단하지는 않는다. 새 버전의 규칙은
  재빌드한 새 실행부터 적용하며, 다른 버전의 결과를 무심코 합치지 않는다.

## 아키텍처 결정

### 1. 시뮬레이션 경로
- Rust 어댑터(`gaia-rl` 크레이트, 이 디렉토리)가 `gaia_engine::RuleEngine`/`ScoringEngine`/
  `Randomizer`를 직접 호출.
- PyO3로 Python에 노출. Python 쪽은 PettingZoo의 **AEC(Agent-Environment-Cycle)** API —
  턴제 다인 게임이라 동시행동 Gym API보다 이게 자연스럽다.

### 2. 관측(observation) 인코딩
- 1차: 손으로 설계한 평면 특징 벡터 (자원/연구 트랙 레벨/구조물 수/보드 요약/라운드-페이즈).
- 그래프/CNN 기반 보드 인코더 등은 파이프라인이 끝까지 도는 걸 확인한 뒤 나중에.

### 3. 행동(action) 표현 — 이게 제일 중요한 결정
`RuleEngine::get_valid_actions(state, player)`가 **매 결정 시점마다 이미 구체적으로
열거된** `Vec<GameAction>`을 준다 (참고: 이 함수의 QIC 사거리 연장 열거 누락 버그를 이번
세션에서 고쳤음 — `gaia-engine/src/rules/engine.rs`). 그래서 고정 크기 discrete action
space를 억지로 설계할 필요가 없다.

**채택한 방식 — 후보 스코어링(candidate scoring)**: 각 후보 `GameAction`을 작은 특징
벡터로 인코딩 → 상태 임베딩과 합쳐서 공유 MLP로 점수 하나씩 산출 → 그 점수들에 softmax →
학습 중엔 샘플링, 평가 중엔 argmax. 조합적/파라메트릭 행동 공간의 표준 기법.

### 4. 신경망 구조
정책망/가치망을 **완전히 분리된 네트워크 2개로 만들지 않는다.** 하나의 공유 몸통(상태
인코더) + 출력 헤드 2개:
- 가치 헤드: 상태 임베딩만 보고 스칼라 하나.
- 정책(후보 스코어링) 헤드: 상태 임베딩 + 각 후보 액션 임베딩 → 후보별 점수.

이유: 상태 표현이 두 헤드 사이에 전이돼서 샘플 효율이 좋음. 학습이 불안정해지면(정책/가치
신호가 서로 방해) 그때 가서 분리 고려 — 지금부터 나눌 필요 없음.

### 5. 보상
`ScoringEngine::calculate_final_scoring`의 최종 VP를 제로섬 정규화해서 종국 보상으로 사용.
한 게임이 원자적 행동 기준 수백 스텝일 수 있어 크레딧 할당이 어려울 수 있음 — 필요하면
나중에 매크로 액션 묶기(한 플레이어의 한 턴 전체를 하나의 결정 단위로)로 스텝 수를 줄이는
것을 고려.

### 6. 학습 알고리즘 — PPO 셀프플레이 (MCTS/AlphaZero는 스트레치 골)
4석 모두 정책 공유(parameter sharing), PPO, Ray RLlib으로 분산 롤아웃.

**MCTS/AlphaZero류를 먼저 안 하는 이유** (자세한 트레이드오프는 대화 기록 참고):
- 4인 **일반합**(비제로섬) 게임이라 셀프플레이 수렴에 대한 이론적 보장이 없음 — 2인
  제로섬 전제로 만들어진 원조 AlphaZero와 근본적으로 다른 문제.
- 가변 행동 공간이라 매 노드 확장(expand)마다 신경망 forward가 필요해 시뮬레이션당 비용이
  가변적이고 큼.
- 게임이 길어서(수백 원자적 액션) 시뮬레이션 예산 관리가 까다로움.
- **참고**: 게임 도중 확률적 전이(주사위 등)는 없음(셋업 시드 이후로는 전부 플레이어
  선택) — 확인됨. 그래서 MCTS를 나중에 하게 되면 chance node 없이 순수 결정적 트리로 가능.
- **만약 MCTS로 간다면**: 매 시뮬레이션마다 게임 끝까지 안 내려가고, 리시딩 호라이즌
  (수 라운드 앞만 보고 나머지는 가치망에 맡김, 체스 엔진의 고정 깊이 탐색과 같은 발상)으로
  가는 게 맞다는 결론까지는 논의됨. 원자적 액션 개수가 라운드마다 들쭉날쭉하니 깊이 제한은
  "N 라운드"가 아니라 "N ply(원자적 액션 수)"로 잡는 게 나음.

**권장 순서**: PPO로 파이프라인 전체(환경→학습→평가)를 먼저 끝까지 돌려서 "학습이 되긴
하는지" 확인 → 그 결과와 여유(시간/컴퓨팅)를 보고 MCTS 확장 여부 결정.

### 7. 종족(faction) 처리 — 하나의 제너럴리스트 정책 (종족별 전문 AI 9개 아님)
18개 종족을 종족 ID를 입력으로 받는 **하나의 공유 정책망**으로 처리하기로 함. "종족쌍(같은
물리 보드 양면)은 같은 게임에 절대 같이 안 나온다"(`FactionId::other_board_side`, 9쌍)는
사실은 맞지만, 그렇다고 9개 전문 AI로 나누는 게 더 나아지진 않음 — 이유:
- 셀프플레이 매치메이킹 복잡도 (9개를 매 게임 4석에 어떻게 배정할지)
- 종족별 경험량 불균형 (게임마다 18개 중 4개만 등장)
- 공통 전략(헥스 확장 타이밍, 연방 형성 등) 재사용 손실 — 9개 따로면 각자 처음부터 배워야 함

나중에 제너럴리스트가 정체되면 "공유 트렁크 + 종족별 헤드"(멀티태스크 학습) 절충안을 고려
— 지금 결정할 필요는 없음.

### 8. 난이도 조절 (배포용 봇 강도)
1. **온도(temperature) 샘플링** — 후보 점수 softmax 온도 조절, 재학습 없이 추론 시점에
   바로 조절 가능. 1순위 추천.
2. **체크포인트 선택** — 초반 체크포인트=쉬움, 최종본=어려움.
3. (MCTS로 가면) 시뮬레이션 예산 조절.

## 현재 상태 (2026-09-10, 플레이 연결 전)

진행 기준: `../.omx/plans/gaia-rl-training-evaluation.md`의 승인된 M0–M4 단계.

- 구현: 엔진 직접 호출, 구체적 합법 후보, 결정권자/결정 ID 검증, 원자적 실패,
  종국 점수/보상, 정확한 연방 후보와 동률 최소 위성 경로.
- 구현: PyO3 + PettingZoo AEC, 실제 위치 보존 평면 관측/후보 인코딩,
  공유 몸통 + 후보 점수 헤드 + 가치 헤드, 로컬 RLlib PPO 실행기.
- 구현: 모델/옵티마이저/RNG 저장·재개, 버전 불일치 거부, 별도 추론 경계,
  무작위/고정 체크포인트 상대 평가와 4석 회전.
- 검증: Python 15개 검사 및 PettingZoo API 검사, 후보 순서 변경에 대한 정책
  점수 대응/마스크/유한 gradient, Rust AI 결정 검사 7개.
- 통합 파일럿: CPU에서 1회 학습 → 저장 → 새 알고리즘에 복원 → 추가 1회 학습.
  모델 가중치와 옵티마이저의 정확한 복원을 비교 검증했고 손실값은 유한했다.
  이어 무작위 상대 8게임 + 고정 모델 상대 8게임을 모두 완주했다.
  최종 검증 전체 약 94초, 드라이버 최대 RSS 약 1,374 MiB (Ray 전체 합계는 아님).
- 파일럿 모델 평가: 무작위 상대 승리 지분 37.5%, 고정 모델 상대 12.5%.
  각각 2개 시드뿐이며 **실력 향상이 입증된 모델이 아니다**. 학습·평가 경로의
  동작 검증용 체크포인트다. 플레이 강도 확보에는 별도 장시간 학습/평가가 필요하다.
- 통합 증거: `runs/integrated-pilot-v2/report.json`, 모델은 해당 디렉터리의
  `initial/`, `resumed/`. 실행 명령과 제한은 `README.md`에 기록했다.
- **범위 밖으로 남김**: 서버/UI AI 참가 연결, 규칙 변경 간 모델 전이,
  난이도 UI, 장시간 학습, 중단한 보드의 정확한 중간 턴 복원.
  재개는 학습 상태/RNG를 복원한 뒤 다음 새 게임부터 시작한다.

장시간 학습 전에는 최신 엔진의 검증 결과와 규칙 안정성을 확인한다. 게임 코드가
계속 바뀌는 동안 나온 검증 결과는 보고서의 엔진 fingerprint에만 해당한다.

## 학습 시간/난이도 추정 (거친 추정치, M0 실측 전)

- 난이도: 표준 RL 튜토리얼보다 확실히 위, "학계 소논문 급 보드게임 RL 프로젝트"에 가까움.
  가변 행동 공간 + 비제로섬 4인 + 지연 보상 + 사전학습 자산 전무.
- 파이프라인 구축(개발) 자체는 혼자 파트타임 기준 수 주 단위로 추정.
- 실제 학습 시간은 10^7~10^8 스텝 규모로 추정(이 게임 복잡도 기준), 개인 컴퓨터에서
  초당 처리량 100~1000스텝 가정 시 몇 시간~1-2주 범위 — **불확실성이 매우 큼**. M0에서
  "이 머신이 초당 게임을 몇 번 시뮬레이션할 수 있는지"부터 실측하는 게 진짜 견적의 시작점.

## 참고 자료 (2026-09 검색으로 확인)

- [PyTAG: Tabletop Games for Multi-Agent Reinforcement Learning](https://arxiv.org/html/2405.18123v1)
  — 복잡한 테이블탑 게임을 RL 환경으로 감싸는 툴킷. 우리가 하려는 것과 구조적으로 거의 동일.
- [Reinforcement Learning Agents Playing Ticket to Ride](https://www.researchgate.net/publication/371649650_Reinforcement_Learning_Agents_Playing_Ticket_to_Ride-A_Complex_Imperfect_Information_Board_Game_With_Delayed_Rewards)
  — 큰 상태-행동 공간 + 지연 보상 보드게임에 PPO 셀프플레이 적용 사례. 성격이 제일 비슷함.
- [RainbowArena](https://www.sciencedirect.com/science/article/abs/pii/S0950705125020842) —
  테이블탑 게임용 RL/LLM 멀티에이전트 툴킷, 여러 셀프플레이 학습법 비교 실험 (2025).
- [PettingZoo 공식 RLlib 튜토리얼](https://pettingzoo.farama.org/tutorials/rllib/index.html)
  — Leduc Hold'em 예제의 illegal action masking = 우리가 쓸 "합법 후보만 스코어링"과 동일 개념.
- [RLlib PettingZoo parameter-sharing 예제](https://github.com/ray-project/ray/blob/master/rllib/examples/multi_agent/pettingzoo_parameter_sharing.py)
  — "4석 모두 정책 공유" 구조의 실제 구현 예시.

읽는 순서 추천: PettingZoo RLlib 튜토리얼(실습) → Ticket to Ride 논문(비슷한 문제 사례) →
PyTAG(환경 설계 참고).

## 열린 질문 / 나중에 결정할 것

- M0을 언제 시작할지 (gaia-engine 워크스페이스 안정성에 달림).
- 매크로 액션 묶기를 실제로 할지 (에피소드 길이 문제가 M2 실측에서 얼마나 심각한지 보고).
- MCTS 확장 여부 (PPO 결과를 보고 판단).
- 종족 제너럴리스트가 정체되면 멀티태스크 헤드 절충안으로 갈지.
