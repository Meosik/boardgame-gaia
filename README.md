# Gaia

Server-authoritative, four-player browser implementation of **Gaia Project** with the **Lost Fleet** expansion.

> **Current status:** architecture foundation and legacy cleanup are in progress. The repository builds and its available tests pass. Room control revision, command idempotency, atomic PostgreSQL command storage, and restart/reconnect recovery are implemented over the gaia-protocol envelope. The round loop now actually completes end to end (Gaia phase, Income phase, and the round→round phase transition were previously unwired — a round-2 game was stuck forever) and round-tile VP is now applied instead of only broadcast; the complete official setup, full six-round rules engine, and browser E2E acceptance scenario are still not finished — see "Known migration work".

## Product scenario

1. A host creates a guest room and receives a short room code plus an opaque seat-recovery token.
2. Exactly three additional guests join. A fifth player cannot claim a seat.
3. The server creates a deterministic Lost Fleet setup from a versioned seed.
4. Players choose factions sequentially in official player order. The first release uses clockwise turn order; legacy bidding is not part of the target product.
5. The final player may rotate Space Sector tiles through persisted setup commands before confirming the board. Lost Fleet spaceship tiles must be at least four axial-hex spaces apart.
6. The authoritative Rust engine validates every setup and gameplay command. Rejected commands cannot partially mutate state.
7. Players complete Income, Gaia, Action, and Clean-up phases for rounds 1–6. The same pure transition path serves live play, tests, and recovery.
8. If any required player disconnects, gameplay pauses without changing the gameplay revision. Reconnection uses the seat token and returns an authoritative snapshot before play resumes.
9. PostgreSQL atomically stores accepted command identity, events/audit data, the new revision, and authoritative post-state. Restart recovery never depends on live sockets.
10. After round 6, the server applies official final scoring and publishes the terminal result to all four clients.

## Architecture

```text
gaia-frontend (React/Vite)
        | REST + versioned WebSocket
gaia-server (Axum/Tokio coordinator)
        | strict envelopes from gaia-protocol
gaia-engine (pure deterministic rules)
        |
PostgreSQL (authoritative durable state)
```

- `gaia-protocol`: strict command IDs, JavaScript-safe revisions, seat IDs, digests, and versioned envelopes.
- `gaia-engine`: domain state and deterministic rule transitions. Existing legacy rules/data remain under replacement.
- `gaia-server`: room/session transport, persistence, and browser delivery.
- `gaia-frontend`: browser UI and WebSocket client.
- `.omx/plans`: current PRD, test specification, architecture review, and cleanup plan.

AI coaching, MCTS, Qdrant, and Ollama were removed because they are explicit non-goals for the core game.

## Local development

Prerequisites:

- Rust 1.95.0 (`rust-toolchain.toml`)
- Node.js 24.19.0 (`.nvmrc`)
- Docker with Compose

Start PostgreSQL:

```bash
docker compose -f docker-compose.dev.yml up -d
cp gaia-server/.env.example gaia-server/.env
cargo run -p gaia-server
```

In another terminal:

```bash
cd gaia-frontend
npm ci
npm run dev
```

Build the combined server/client image:

```bash
docker compose up --build
```

## Known migration work

- **`MapEngine::place_deep_space_sectors` now places each of the 8 Deep Space sectors in the specific gap between one pair of adjacent Standard sectors, one gap per sector, instead of anywhere valid along the boundary.** The project owner reported Deep Space tiles kept appearing "in the wrong place" — explained in part by `MapEngine::init_game_state` seeding its `Randomizer` with the room code itself, so repeatedly testing in the same room reproduces the exact same layout every time, not fresh randomness each attempt. Two earlier attempts at a fix were tried, measured, and reverted before landing on the real cause: (1) the original code took the *first* non-overlapping `(anchor, rotation)` in shuffle order anywhere along the boundary, with nothing constraining *where* — this let two Deep Space tiles cluster next to the same Standard sector while others bordered none, which is what "각 번호 우주 보드 사이에 위치하면 되는걸" (it should just sit between each numbered sector) was pointing at. (2) A first fix attempt maximized shared-edge "snugness" instead, which was checked against a reference randomizer tool (screenshot: sectors 11-18 each touching the board at only 1-2 hexes) and found to over-nest tiles into single tight pockets regardless of *which* gap, not spread them around the perimeter — reverted. The actual fix: `lost_fleet_sector_origins`'s 10 origins are `[A, B, ring[0..8]]`, where `A`/`B` are the 2 fully-interior "center" sectors (surrounded on every side, never touching the outside) and the 8 ring positions form a single cycle of tight (distance-5, 3-hex-shared-border) adjacency — verified by brute-force pairwise distance search, not assumed. `deep_space_gap_candidates` computes, for each of the 8 consecutive ring pairs around that cycle, every empty hex that touches *both* neighboring sectors' 19-hex disks (the natural notch between them); `place_deep_space_sectors` shuffle-assigns one gap's candidate list to each Deep Space sector and searches only within it. New regression test `eight_deep_space_sectors_each_sit_between_exactly_two_standard_sectors` asserts every Deep Space sector borders exactly 2 Standard sectors, and that the 8 ring sectors are each bordered by exactly 2 (while the 2 interior centers are bordered by none) — verified across 25 seeds.

- **QIC-based range extension is implemented** (rulebook p.11, "Build a Mine": "you can spend any number of Q.I.C. to increase your range by two spaces for each Q.I.C. spent" — confirmed by the worked example, Navigation level 2 / basic range 2 / spend 1 QIC → range 4). Rather than exposing a separate "how much QIC to spend" choice, `range_and_qic_cost` (`gaia-engine/src/rules/engine.rs`) and `MapEngine::shortest_distance` (`gaia-engine/src/map/engine.rs`, a bounded-BFS variant of `reachable_hexes` that returns the actual hex-step distance instead of a reachable set) auto-compute the minimum QIC needed to reach a given target, matching every other derived cost in this engine. Wired into `Build`, `GaiaFormation`, and Lost Fleet's `ExploreSpaceship` — the Lost Fleet rulebook explicitly reuses the identical base-game rule for both ("you may still spend Q.I.C.s to increase your range... just like when you increase the range of the 'Build a Mine' or 'Start a Gaia Project' actions"). Not yet wired into `get_valid_actions`'s candidate-hex enumeration (still nav-range-only there — a pre-existing, already-documented gap, not a new one), so QIC-extended targets are accepted by `validate_action` but won't appear in the "valid targets" list the AI sidecar/client highlighting would use.
- All 18 factions' starting resource bowls (ore/credits/knowledge/QIC/power) in `gaia-engine/data/factions.toml` are now confirmed against the physical faction board scans (transcribed directly by the project owner, since the rulebook only prints faction abilities in prose, not the boards' numeric bowls). Starting research-track levels (`starting_track_bonuses`) are likewise confirmed against `gaia-frontend/src/assets/faction_boards/` — 12 of the 18 factions start with one research track (two for Darkanians) at level 1 instead of 0, a detail the rulebook prose never mentions either.
- Per-structure round income (Mine/TradingStation/ResearchLab base+table, Academy(Science), PlanetaryInstitute power charge) is wired into `apply_income_phase` (`gaia-engine/src/rules/engine.rs`, `apply_structure_income`). Values are universal across factions (Mine: 1 ore base + `[1,1,0,1,1,1,1,1]`; TradingStation: 0 credits base + `[3,4,4,5]`; ResearchLab: 1 knowledge base + `[1,1,1]`; Academy(Science): 2 knowledge/round; PlanetaryInstitute: charge 4 power/round) unless a faction's `factions.toml` entry overrides them — confirmed overrides: Firaks' ResearchLab base (2 knowledge), Bescods' TradingStation/ResearchLab income swap (TradingStation pays knowledge, ResearchLab pays credits), Nevlas' ResearchLab income (2/2/2 power instead of knowledge), Itars' Academy(Science) (3 knowledge/round), Space Giants' PlanetaryInstitute charge (6 power/round). All 18 factions' data is transcribed from the physical faction boards.

  PlanetaryInstitute's per-round bonus power token (universal: +1/round, entering bowl1 fresh; Lantids: 0; Ambas/Bescods: +2/round) is implemented, including the order choice it creates: since the fresh token can itself get swept into the same round's power charge if it enters bowl1 before the charge is applied, a player with both effects must choose which happens first. `apply_income_phase` defers any such player into `GamePhase::IncomeOrderPending` (queue-front processing, like `ChargePowerPending`) instead of applying the charge immediately; each queued player resolves their own entry with `GameAction::ChooseIncomeOrder { charge_first }`, and the round only finishes (round increments, `ActionPhase` reopens) once the queue drains. PlanetaryInstitute's per-round bonus *resource* (Xenos: 1 QIC instead of a power token; Gleens: 1 ore instead; Ivits: 1 QIC alongside its normal power token) is also implemented (`FactionData.planetary_institute_bonus_resource`), applied directly since it has no charge-order interaction. Terrans' and Itars' interactive Gaia-phase abilities use `GamePhase::GaiaDecisionPending`. The remaining base-faction PI rules now handled centrally are Xenos' six-power federation threshold, Ambas' once-per-round PI↔Mine swap, Geodens' 3-knowledge first-post-PI-colonization reward, Bal T'aks' Navigation unlock, Firaks' ResearchLab downgrade, Bescods' +1 home-planet structure power, and Nevlas' doubled Area III power-action spending.

  Academy(Qic)'s action — "gain 1 Q.I.C." (rulebook p.13), requires a built Academy(Qic) — is implemented as `GameAction::AcademyQicAction`, including BalTaks' override (gain 4 credits instead, `factions.toml`'s `academy_qic_action`). Per rulebook p.15 ("Special Actions": free, but limited to once per round via an action token, reset at Clean-up), it's capped at once per round via `PlayerState.academy_qic_action_used_this_round`, reset in `finish_round_transition` alongside `passed`; the frontend button disables itself accordingly.

  The shared power-action board (rulebook Appendix III: "each of these actions can be taken only once per round," exclusive across *all* players, not just per-player like Academy(Qic) above) is enforced via `GameState.used_power_actions` (`Vec<u8>`, board slot ids taken this round) — `validate_power_action` rejects a slot already in it, `apply_power_action` pushes onto it, and `finish_round_transition` clears it alongside the Academy(Qic) flag. The frontend's `PowerAction` picker disables already-taken slots the same way the Academy(Qic) button does.

  **The QIC-action board doesn't exist in this project.** A prior pass had implemented a fabricated `GameAction::QicAction`/`QicActionKind` (GainOre/ResearchStep/BuildSatellite/ColoniseLostPlanet) that never matched any real rulebook mechanic — confirmed by cropping `gaia-frontend/src/assets/boards/research_board.jpg`'s actual QIC row (3 slots, not 4, with entirely different effects: build-with-terraforming-steps, score-a-federation-token-again, VP-per-planet-type) and separately confirmed that this project's Lost Fleet board piece physically covers **all 3** of those real slots with the ProtoPlanet/Asteroid terraforming rule (see the tech-tile research notes) — so under this project's always-Lost-Fleet ruleset, no QIC-action board space is ever actually in play. `QicAction`/`QicActionKind` have been removed entirely (engine, wire protocol, and frontend) rather than fixed; the QIC *resource* itself is untouched (Academy(Qic), advanced tech tile requirements, and free actions still use it).

  **The power-action board's costs/effects were also fabricated** and have been corrected against the same board image — the previously-shipped `[3,4,4,4,4,6,4]` cost table and its resource grants didn't match the real `[7,5,4,4,4,3,3]` board at all. The two "free terraforming steps" slots (ids 2 and 6) needed real engineering, not just a number fix: they immediately perform a `Build`-equivalent action (now `GameAction::PowerAction { id, coord }`, `coord` required only for these two slots) via a shared `validate_build_impl`/`apply_build_impl` that both the normal `Build` action and these two slots call, parameterized by free terraforming steps and an extra power cost. Slot 7 ("+2 power tokens to bowl1") adds fresh tokens the same way the PlanetaryInstitute bonus token does — not a charge (which moves *existing* tokens forward).

  **Lost Fleet's two new main actions are implemented**: `GameAction::ExploreSpaceship { ship }` ("11) Action: Explore a Lost Fleet Spaceship") and `GameAction::ExamineArtifact` ("12) Action: Examine an Artifact") — see `docs/GP_Exp_Rule_EN_V1_Web.pdf`. This turned out to be a much bigger system than the earlier QIC-board-overlay/Scoring-Board-Extension work above implied: there are **4 separate spaceship boards** (Twilight/Rebellion/T F Mars/Eclipse, `GameState.spaceship_boards`), each with its own shuttle-slot queue (`PlayerState.exploration_shuttles_available`, 3 per player) and, for Twilight only, an Artifact pool. Exploring costs 5 VP and requires the target spaceship's map hex in range; anyone after the first explorer on a given ship immediately charges power per `spaceship_shuttle_power_charge`'s slot table `[0, 2, 2, 3]` — confirmed against a physical shuttle-slot photo (a first pass misread a low-resolution PDF render of the same slots as "all identical, flat 1"; the photo showed the digits the render couldn't resolve). Examining an Artifact requires an explored Twilight shuttle and discards 6 power total to take one. **`ExamineArtifact` now takes a chosen `artifact: ArtifactId` instead of always drawing blind index 0** — the rulebook's "gain 1 artifact from the spaceship" reflects the physical components being laid out face-up and picked, not drawn from a face-down deck (confirmed with the project owner); `validate_examine_artifact` checks the chosen id is actually still in the Twilight board's `artifact_pool` before removing it. All 13 physical Artifact tokens' effects (rulebook Appendix VII) are confirmed directly from individual token photos (`gaia-frontend/src/assets/artifacts/artifact_01`–`_13`) and modeled (`artifact_effect` in `rules/engine.rs`): 2 VP per colonized Deep Space sector; +2 power directly into bowl3; 1 ore + 1 knowledge; 3 VP per Gaia Project research-track level; 3 VP per Science research-track level (this one also matches the rulebook Appendix VII page's own worked example, Science level 5 → 15 VP); 3 credits + 3 ore; 3 knowledge + 1 QIC; flat 7 VP (the rulebook's "also counts as a phantom asteroid/protoplanet mine" clause on this last one isn't modeled yet); 5 credits + 2 ore; **id 10, "copy the effect of a Federation Token you own," is now implemented too** — `ExamineArtifact` gained `copy_federation_token_kind`/`bonus_build_coord`/`bonus_tech_tile`/`bonus_research_track` fields (required exactly when the chosen artifact is id 10), and the shared replay logic that used to live only inside `apply_twilight_replay_federation_token` was extracted into `validate_owned_federation_token_effect`/`apply_owned_federation_token_effect` so both Twilight's "Score a Federation Token Again" action space and this Artifact reuse the identical mechanism rather than duplicating it; 3 VP plus 1 VP per distinct colonized planet type (reuses `ScoringEngine::final_scoring_metric`'s `MostPlanetTypes` counting logic); another flat 7 VP whose own "colonize 1 Asteroid" clause isn't modeled yet either, for the same reason as artifact 8 — the "Examine an Artifact" action takes no coordinate to build a phantom mine at; and 3 VP for each research track at level 3 or higher. An earlier pass had only 4 of these confirmed, sourced from a small rulebook icon grid rather than individual photos — two of those four turned out to be misidentified once the real per-token photos arrived (a guessed "federation token" icon was actually the Gaia Project research track; a guessed "3 VP per track at level 3+" effect didn't appear among the first 8 individually-photographed tokens, but *did* turn out to be real once the last 5 photos arrived — it's id 13 above). `GameAction::Build`'s Asteroid/Protoplanet branches are also now real: Protoplanet costs a flat 3 terraforming steps (not ring-distance) and grants +6 VP; Asteroid consumes a Gaiaformer permanently (`Resources.spent_gaia_formers`, distinct from the reusable `gaiaformers_deployed`) and waives the mine's ore/credit cost entirely. **The real 4-player Interspace-tile variable map setup is now implemented** (rulebook p.4-5), replacing an earlier simplified stand-in that dropped the 4 spaceship tiles as extra hexes just outside an ordinary sector ring. `Randomizer::build_sector_layout` places 2 of sectors 01-04 as a center "domino" and the other 8 (the remaining 2 of 01-04, plus 05-10) around them, using 10 origins derived from `tight_sector_directions()` — the 6 canonical `HexCoord::rotate_60`-cycle offsets (starting at `(-5, 1)`) giving zero-overlap, 3-hex-border ("as per the base game") adjacency between two 19-hex sector disks; this was brute-force-verified before writing any placement code, not hand-tuned. That specific "2 centers + 8 ring" topology, unlike a naive tight tiling, produces exactly 10 triangular triple-junctions among the 19 pairwise-adjacent sectors, each with exactly one hex touching all 3 disks and belonging to none — `MapEngine::find_interspace_holes` locates these 10 single-hex gaps generically (any 3 sector origins, not hardcoded per-triangle). `MapEngine::place_interspace_tiles` then shuffle-assigns the 10-tile pool (4 `SpaceshipId`s, 4 Asteroid, 1 ProtoPlanet, 1 blank) into those holes, retrying until no two spaceship tiles are within 3 spaces of each other (rulebook constraint); the blank tile is inserted as a real empty walkable hex. `MapEngine::place_deep_space_sectors` computes real origins for the 8 Deep Space sectors (`Randomizer::build_deep_space_layout` only shuffles their ids/sides now, since their board-dependent placement needs the assembled standard board to exist first) by searching the assembled board's outer boundary for non-overlapping 3-hex-tromino pockets at random rotations. Property tests (`tests/unit/lost_fleet_map_layout.rs`) verify all of this holds across 25 seeds: 190 unique standard-sector hexes, exactly 10 holes each bordering exactly 3 distinct sectors, all 4 spaceship tiles present and pairwise ≥3 apart, all 8 Deep Space sectors non-overlapping with real (non-placeholder) origins, and the whole 224-hex board staying a single connected component.

  **All 12 of the 4 spaceships' Appendix II ("New Action Spaces") actions are implemented.** `GameAction::SpaceshipCreditTerraform { coord }` — "the same as the power action 'Take 1 free terraforming step,' except it costs 3 credits" — was originally modeled as unlocked by exploring *any* spaceship, since which ship it belonged to wasn't yet identified; it's since been confirmed as T F Mars' third action slot and re-gated accordingly (`validate_spaceship_credit_terraform` now requires T F Mars explored specifically, matching every other Appendix II action's per-ship gating). `GameAction::TwilightFreeResearchLab { coord }` costs 3 power + 2 ore to activate, then grants a Trading Station → Research Lab upgrade at no *additional* ore/credit cost, gated on Twilight explored; `GameAction::RebellionFreeTradingStation { coord }` mirrors it (3 power + 1 ore, Mine → Trading Station, gated on Rebellion explored) — both reuse `Upgrade`'s logic via a `free: bool` parameter on `validate_upgrade_impl`/`apply_upgrade_impl`. `GameAction::RebellionCreditsAndQic` costs 2 knowledge for a flat one-time 2 credits + 1 QIC, no coord needed. `GameAction::TFMarsTechBonus` costs 2 QIC for a flat one-time 2 VP plus 1 additional VP per Standard Tech tile owned (`PlayerState.tech_tiles.len()`), no coord needed. `GameAction::TFMarsGaiaFormation { coord }` is the expansion's immediate Gaia action: it costs 2 power from bowl3 regardless of Gaia Project track level, moves no power into the Gaia area, immediately flips the reserved Transdim planet to Gaia, and leaves the temporarily used Gaiaformer available again in the same round; range remains QIC-extendable. `GameAction::EclipsePlanetTypeBonus` mirrors `TFMarsTechBonus`'s shape (2 QIC, flat 2 VP) but counts distinct colonized planet types instead of tech tiles, reusing `ScoringEngine::final_scoring_metric`'s `MostPlanetTypes` counting logic (the same helper `artifact_11`'s effect uses). `GameAction::EclipseResearchBoost { track }` is an alternative to `ResearchAdvance` — 3 power + 2 knowledge instead of the base game's flat 4 knowledge (`RESEARCH_KNOWLEDGE_COST`) — otherwise identical (track-max check, round-tile-bonus check). `GameAction::EclipseAsteroidMine { coord }` is an alternative to `Build`'s Asteroid branch — 6 credits activation fee instead of that branch's usual zero ore/credit cost — restricted to Asteroid-type targets specifically (`Build`/`SpaceshipCreditTerraform`'s shared `validate_build_impl` would otherwise accept any buildable planet type, so this action adds its own planet-type check before delegating). All 12 share one shared once-per-round exclusivity pool (`GameState.used_spaceship_actions`, ids 1-12 — cleared with the other action tokens during round Clean-up; the three target modes of Twilight's single +3-range space all use id 11). The remaining spaces are `TwilightReplayFederationToken` (3 QIC, replay an owned token without consuming or gaining a token, including its target/Tech-tile follow-up), `TwilightRangeBuild`/`TwilightRangeGaiaFormation`/`TwilightRangeExploreSpaceship` (1 knowledge, one immediate action with +3 range), and `RebellionGainTechTile` (3 QIC, take an available Standard Tech tile and advance the chosen research track). `get_valid_actions`, the browser action panel, and shared-slot disabling all expose the same choices.

  **Federation tokens now have real rewards.** `apply_federation` previously granted the same hardcoded `FederationToken(1)` with no VP or resources at all; `GameAction::FormFederation` now takes a `token: FederationTokenChoice` (`Supply { kind }` from the general 19-token pool, or `Spaceship { ship }` claiming one of the 4 Lost Fleet spaceship-tied tokens — expansion p.5, "if you have an Exploration Shuttle on a Lost Fleet spaceship and there is still a Federation token there, you can gain that token when you form a Federation") plus optional `bonus_build_coord`/`bonus_tech_tile` fields for the two token kinds that grant a follow-up action. The 19-token base supply (`docs/EN_Gaia_rulebook_lo.pdf` p.2 components image, cross-checked against individual photos at `gaia-frontend/src/assets/federation_tokens/`) is seeded at setup into `ResearchBoard.federation_tokens`: 12 VP ×3; 8 VP + 1 QIC ×3 (the rulebook crop's green hex icon here was first misread as ore — caught once `fed_token_03_score_8_vp_and_gain_1_qic.jpg`'s filename, and later the token's own photo, confirmed QIC); 8 VP + 2 power (fresh bowl1 tokens) ×3; 7 VP + 2 ore ×3; 7 VP + 6 credits ×3; 6 VP + 2 knowledge ×3; 1 ore + 1 knowledge + 2 credits (no VP) ×1. (`fed_token_02` through `_07` were corrupted, non-image binary data the first time they were checked — later replaced with valid photos that confirmed every one of the 7 ids, including id 5, whose photo initially looked inconsistent — gray side showing "7"/"6", green side "9"/an upside-down "7" — until the mismatch turned out to just be the green side photographed rotated 180°: a "6" rotated 180° reads as "9", explaining the apparent conflict without changing the underlying "7 VP + 6 credits" reward. Every photographed token shows the identical reward icons on both its green and gray backing once rotation is accounted for — the color is purely cosmetic, not a second set of data — so there's nothing extra to model here even before the flip mechanic below exists.) The 8 Lost Fleet tokens (`gaia-frontend/src/assets/federation_tokens_lost_fleet/`, one seeded per spaceship board at setup, one drawn per ship from the 8-entry pool) are **8 distinct physical tokens, not 2 copies of 4 kinds** — Appendix VI's page only spells out 4 of the 8 in prose (the other 4 apparently went unwritten since they just follow the base game's already-explained "VP + resources" pattern); all 8 are now individually photo-confirmed: 8 VP + 8 credits; 12 VP (the rulebook notes this specific variant stays flippable for Advanced Tech/level-5 research even after use — the flip-spend mechanic itself still isn't modeled, see below, so it's modeled as plain 12 VP); 4 VP + 4 knowledge; 4 VP + 2 ore + 1 QIC; 1 Standard Tech tile of the player's choice; 7 VP + 2 power as **fresh tokens directly into bowl3** ("Area III" — an earlier verbal description of this one as "charged" turned out to be imprecise once the photo arrived showing the same fresh-grant icon style as the base game's "8 VP + 2 power," just targeting bowl3 instead of bowl1); a free `Build` with up to 3 free terraforming steps (normal QIC-extendable range); and a free `Build` of limitless range (`validate_build_impl`/`apply_build_impl` gained an `unlimited_range: bool` parameter that skips reachability/QIC-for-range entirely — ore still costs for terraforming, QIC still costs for Gaia planets). **The green/gray token-flip system is now implemented too** (rulebook p.14: "you must flip one of your federation tokens from its green side to its gray side... this is the same cost as for taking an advanced tech tile"; p.15: "You must own at least one federation token with its green side faceup. To take the advanced tech tile, flip one of your federation tokens to its gray side"). `PlayerState.gray_federation_tokens` holds flipped tokens separately from the still-spendable `federation_tokens`; `flip_a_federation_token` moves one across (arbitrary draw order — the flip has no reward attached, so which physical token moves doesn't matter) whenever a player reaches research level 5 or takes an Advanced Tech tile, gated by `validate_has_a_green_federation_token`. See the Research-track paragraph below for level 5 specifically, and the Tech tile paragraph for the Advanced-tile side. **Satellite-based federation connectivity is now implemented**, closing what used to be the other out-of-scope item: `GameAction::FormFederation` gained a `satellite_hexes: Vec<HexCoord>` field alongside the existing `hexes` (colonized planets) — rulebook p.14, "Connecting Planets": "To connect planets that are not adjacent, you must immediately build satellites... discard one power [per satellite]... place it in a space adjacent to either one of your colonized planets or one of your satellites." `validate_federation` now requires every `hexes` entry to actually be a structure the player owns (a real, if minor, correctness fix uncovered while rewriting this — previously any hex could be listed as a connectivity filler with no ownership check at all), rejects a `satellite_hexes` target that has a planet, a structure, this player's own satellite already there, or coincides with a Lost Fleet spaceship tile (expansion rulebook: "you may not place a satellite on a spaceship tile" — now enforceable since satellites are actually placed), and checks connectivity over `hexes ∪ satellite_hexes` together. Satellites cost 1 power each, discarded from any combination of bowls 1/2/3 (mirrors `ExamineArtifact`'s identical "discard N power" draw order) and never contribute to the federation's power-7 threshold (`MapEngine::federation_power` already excluded `StructureType::Satellite`). `PlayerState.federated_hexes` tracks every hex — planet or satellite — ever committed to one of the player's federations, enforcing "each planet and satellite can be part of only one federation" across separate `FormFederation` calls. **The minimality constraint, the adjacency-exclusivity rule, and the per-color satellite supply cap are now all implemented.** Minimality (rulebook p.14: "You cannot form a federation by connecting more planets and satellites than are needed to form it... if the federation would be valid with at least one fewer planet and one fewer satellite, you must change the federation") is checked as a local no-redundant-node property rather than a full minimal-Steiner-tree search across the whole board: `federation_submission_has_redundant_hex` tries dropping each submitted hex one at a time and rejects the submission if the remainder (plus any already-committed federation, for Ivits growth) is still connected and still meets the power threshold on its own — i.e. no single hex in the submission may ever be provably unnecessary, which is what the rulebook's worked example ("the mine and the connecting satellite are not needed... the other satellite is sufficient") actually checks for, not a search for some entirely different, smaller federation elsewhere on the board.
